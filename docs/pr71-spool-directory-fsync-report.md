## БЛОК A. Дефект `ensureSpoolDir()` (`src/modules/ai/paid-settlement.ts`)

### Причина

В PR #70 каталог создавался `mkdir(dir, { recursive: true })`, а синхронизировался `path.dirname(created)`. Но `mkdir` с `recursive` возвращает **первый** созданный каталог, а не конечный. Пример: `base/nested/spool`, где существует только `base`. `mkdir` вернёт `base/nested`, будет выполнен `fsync(base)`. Запись о `spool` лежит в каталоге `base/nested`, и этот каталог не синхронизировался вообще. Единственный `fsync` внутри `spool` (после `rename` файла) не фиксирует запись о самом `spool` в его родителе. После сбоя питания весь каталог spool с уже «сохранённым» перерасходом мог исчезнуть. Для одного нового уровня код работал случайно, потому что первый созданный каталог совпадает с конечным.

### Исправление

- `missingLevels()` находит отсутствующие уровни пути от первого несуществующего предка до конечного каталога (существующие предки не трогаются).
- `ensureSpoolDir()` создаёт каждый уровень отдельным `mkdir` (режим `0700`, `EEXIST` при гонке допускается) и после каждого уровня синхронизирует его **непосредственного родителя**. Порядок строго сверху вниз: сначала `base`, затем `base/a`, затем `base/a/b`. Затем конечный каталог проверяется `assertSpoolDirSafe` (не симлинк, права ужесточены до `0700`).
- Результат `mkdir` больше не используется.
- Обработка `EINVAL`, `ENOTSUP`, `EOPNOTSUPP` сохранена в `fsyncDirectory` и применяется к каждому уровню.
- Реальная ошибка (`EIO` и т.п.) при синхронизации родителя прерывает запись: `settlePaidAccount` выбрасывает `PaidSettlementError` с `spooled: false`. Уже переименованный файл spool не удаляется (удаление файла происходит только после подтверждённой фиксации в PostgreSQL).
- Неудавшаяся синхронизация не забывается: родитель попадает в множество `unsyncedParents`, и следующая запись в spool сначала повторяет эти `fsync` (сверху вниз) и только потом пишет файл. Без этого повтор после `EIO` увидел бы уже существующий каталог и пропустил синхронизацию. Если каталог к тому времени удалён (`ENOENT`), запись из множества снимается.

## Риски и ограничения

1. **Зависит от ФС.** Если ФС не поддерживает `fsync` каталога (`EINVAL`), надёжность создания каталога после сбоя питания не гарантируется. Это ограничение ФС, а не кода.
2. **Множество `unsyncedParents` живёт в памяти процесса.** Если процесс перезапустится после неудачного `fsync`, повторная синхронизация родителей не выполнится: каталог уже существует. Вызывающий код при этом получил `spooled: false` и знает, что запись не считается надёжной. Следующая успешная запись синхронизирует только сам каталог spool после `rename`.
3. **Права.** Права `0700` выставляются на создаваемые уровни и ужесточаются у конечного каталога. Права существующих промежуточных предков (например `LOCAL_STORAGE_DIR`) не меняются.
4. **Прочее без изменений** относительно PR #70: восстановление при неподтверждённом spool блокирует платный AI (fail-closed), диагностика через `overageRecoveryStatus`.
5. **Внешние API не вызывались.** Платные AI, публикации VK/Telegram, deploy, SSH, production DB, `.env` и секреты не затрагивались.
