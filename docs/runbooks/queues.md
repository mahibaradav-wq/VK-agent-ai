# Runbook: очереди публикаций

## Как устроено

- Задание `PublishJob` всегда пишется в PostgreSQL.
- Если задан `REDIS_URL` и `QUEUE_DRIVER=redis`, worker забирает job через BullMQ.
- Без Redis сайт не падает: задача остаётся в БД, статус не становится `published`.
- Повтор той же версии не создаёт второй внешний пост. Успешная цель не отправляется снова.

## Старт worker

```bash
npm run worker
```

Процесс читает `.env`. Нужны `DATABASE_URL` и, для Redis-режима, `REDIS_URL`.

## Частые состояния

| Симптом | Что проверить |
|---|---|
| Задача висит в `pending` | Запущен ли worker. Для Redis — `redis-cli ping` и `QUEUE_DRIVER=redis` |
| `failed` + `integration_not_configured` | Это штатный отказ без токена Telegram, не сбой очереди |
| `requires_manual_check` | Адаптер не подтвердил результат. Нельзя слепо ретраить |
| `failed` + `rate_limit` | Платформа вернула 429. Будет backoff, успешные цели не дублируются |
| Админка «Очередь» пустая или ошибка | Смотрите PostgreSQL `PublishJob`. Redis down не должен помечаться как успешная доставка |

## Что не делать

- Не ставить статус `published` руками «чтобы клиент увидел успех».
- Не удалять строку job, чтобы «переотправить» — используйте новую попытку после ручной проверки.
- Не класть токен бота в переменные worker «на всякий случай». Токен живёт в зашифрованной записи аккаунта.
