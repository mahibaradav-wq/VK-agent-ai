## БЛОК A. Блокирующий дефект в `src/modules/ai/ai-service.ts`

### Дефект

В PR #69 `syncPendingOverage()` ловил любое исключение `recoverPendingOverageSettlements()` и возвращал `null`. `beginPaidAi()` проверял только `recovery && recovery.failed > 0`, поэтому при `null` считал, что проблем нет, резервировал лимит и пускал запрос к платному провайдеру. Так происходило при ошибке `readdir` каталога spool (`EACCES`, `EIO`), при каталоге-симлинке и при любом другом исключении проверки spool. Подтверждённый, но не записанный в PostgreSQL перерасход оставался неучтённым, а кабинет продолжал тратить платные запросы сверх месячного лимита.

Воспроизведение на базовом коде: в spool лежит неподтверждённый перерасход, `readdir` каталога spool падает с `EACCES`, затем вызывается `ai.generate()`. Ожидалось 0 вызовов провайдера, получен 1 (`AssertionError: expected 1 to be +0`). С исправлением тест зелёный.

### Исправление

- `syncPendingOverage()` возвращает размеченное состояние `{ ok: true, summary }` или `{ ok: false, summary | null, error: AiAccountingPendingError }`. Исключение проверки spool больше не превращается в `null`, а `summary.failed > 0` больше не считается нормой.
- Новый `requireSettledOverage()` вызывается в `beginPaidAi()` до транзакции резерва. Если состояние не `ok`, он пишет best-effort аудит `AI_PAID_DENIED` (`details: overage_recovery_pending: <санитизированная причина>`) и выбрасывает `AiAccountingPendingError`.
- `AiAccountingPendingError` (`src/modules/ai/paid-settlement.ts`) наследует `AccessError` со статусом 409, поэтому пользователь видит понятное русское сообщение, а не 500. Поля: `summary` (счётчики восстановления), `diagnostic` (санитизированная причина), `cause` (исходная ошибка, неперечисляемое свойство).
- Все платные пути идут через `beginPaidAi()`: `generate`, `composeAgentPost`, `reviseStudioCard`, а также `ensureReserve()` перед каждой попыткой провайдера, включая fallback. Значит, ни один платный вызов не начнётся при неопределённом состоянии учёта.
- Диагностика и повторное восстановление: новый метод `ai.overageRecoveryStatus(userId, workspaceId)` (право `ai.view`) заново запускает восстановление и возвращает `{ paidAiBlocked, summary, diagnostic }`. Воркер (`src/server/queue/worker.ts`) на каждом `tick()` повторяет восстановление и логирует неполный результат через `sanitizeDiagnosticError`. Как только причина устранена, следующий `tick`, `usage`, `overageRecoveryStatus` или платный запрос восстанавливают учёт и снимают блокировку.
- Бесплатные операции не блокируются: `ai.usage`, `ai.list` и `overageRecoveryStatus` при ошибке восстановления продолжают работать.
- Область блокировки: запись с ошибкой коммита блокирует только свой кабинет (по `workspaceId` из записи). Нечитаемый или повреждённый файл (кабинет неизвестен), а также недоступный каталог блокируют платный AI всех кабинетов, использующих этот spool. Это сознательный fail-closed.

## БЛОК B. Сохранность spool (`src/modules/ai/paid-settlement.ts`)

| Требование | Реализация |
|---|---|
| Атомарность записи и rename | Временный файл `<id>.json.tmp.<pid>.<uuid>` создаётся с флагом `wx` и режимом `0600`, затем `writeFile` → `fsync` → `close` → `rename`. При ошибке записи, `fsync` или `close` временный файл удаляется. При ошибке `rename` он удаляется, а прежняя версия целевого файла остаётся нетронутой |
| fsync родительского каталога | После `rename` выполняется `fsync` каталога spool (`O_RDONLY | O_DIRECTORY`). Если `mkdir` создал каталог, синхронизируется и его родитель. Ошибки `EINVAL`/`ENOTSUP`/`EOPNOTSUPP` («ФС не поддерживает fsync каталога») игнорируются. Любая другая ошибка (например `EIO`) означает `spooled: false`, при этом уже переименованный файл не удаляется и позже восстанавливается |
| Права каталога и файлов | Новый каталог создаётся с `0700`, файлы с `0600`. У существующего каталога с правами шире `0700` они ужесточаются через `chmod`. Каталог-симлинк или путь, который не является каталогом, отклоняется. Файлы spool читаются через `O_NOFOLLOW` с проверкой `isFile()`, а права шире `0600` ужесточаются через `fchmod` |
| Удаление только после фиксации | Файл удаляется только после успешной транзакции PostgreSQL (`committed`) или подтверждения `already_settled` по уникальному `settlementId`. При ошибке коммита запись перезаписывается атомарно с обновлённой диагностикой. Если не удалась и перезапись, исходный файл остаётся |

## БЛОК C. Регрессионные тесты

Файл `src/modules/ai/fail-closed-recovery.test.ts`, 14 тестов на реальной PostgreSQL. Проверяются фактические `UsageRecord.used`, записи `AI_USAGE_OVERAGE`, `AI_USAGE_OVERAGE_RECOVERED`, `AI_PAID_DENIED` и `AiOverageSettlement`, а также число вызовов mock-провайдера. Отказы ФС внедряются через `vi.mock("node:fs/promises")` (`readdir`, `rename`, `open`, `FileHandle.readFile`, `FileHandle.sync`). Без внедрённых ошибок вызовы проходят в реальную ФС.

| Сценарий | Проверка |
|---|---|
| Ошибка доступа к каталогу (`readdir` `EACCES`) | `AiAccountingPendingError` 409, провайдер вызван 0 раз, `used` не изменился, 1 аудит `AI_PAID_DENIED`. `usage` и `list` работают, `overageRecoveryStatus` показывает `EACCES`. После устранения сбоя восстановлено ровно 1 раз, затем нормальная генерация |
| Ошибка чтения spool при работающей БД (`EIO`) | Блокировка, провайдер вызван 0 раз, файл сохранён. После устранения сбоя восстановление, генерация и ровно 1 `AI_USAGE_OVERAGE` |
| Ошибка PostgreSQL при восстановлении | Блокировка (`summary.failed = 1`), провайдер вызван 0 раз. Затем конкурентное восстановление (2 × `overageRecoveryStatus` + `recoverPendingOverageSettlements`) даёт ровно 1 фиксацию. Повторное восстановление ничего не делает, после двух генераций `used = 5` и 1 запись в журнале |
| Ошибка восстановления отдельной записи | Заблокирован только кабинет A, кабинет B восстановлен и работает. После устранения сбоя A восстановлен без двойного списания (`used = 9`) |
| Повреждённый файл spool | Блокировка, провайдер вызван 0 раз, файл не удалён |
| Каталог spool — симлинк | Отклонён, блокировка, провайдер вызван 0 раз |
| fsync файла и каталога, права | `fsync` выполнен для временного файла, каталога spool и родителя нового каталога. Права `0700`/`0600` |
| Ужесточение прав существующих каталога и файла | `0755` → `0700`, `0644` → `0600` |
| Отказ записи (`fsync` временного файла `EIO`) | `spooled: false`, временных файлов не осталось |

| `fsync` каталога не поддерживается (`EINVAL`) | Допустимо, `spooled: true` |
| Файл не удаляется до фиксации | При ошибке PostgreSQL и ошибке перезаписи (`ENOSPC`) исходная запись цела. Удаление происходит только после успешного восстановления |

## Риски и ограничения

1. **Гарантия ограничена долговременностью тома.** Восстановление опирается на файл spool. Если одновременно недоступны PostgreSQL и запись на диск (`spooled: false`) или том `media_data` потерян без бэкапа, автоматическое восстановление невозможно. Остаются `PaidSettlementError` и лог stderr для ручного разбора.
2. **`fsync` каталога зависит от ФС.** На ФС, где `fsync` каталога возвращает `EINVAL`, durability `rename` после сбоя питания не гарантирована. Целевые Linux ФС (ext4, xfs, overlayfs поверх них) это поддерживают.
3. **Широкая блокировка при нечитаемом spool.** Повреждённый файл или недоступный каталог блокируют платный AI всех кабинетов, использующих этот spool, до ручного разбора: файл нужно исправить или переместить из каталога. Так задумано (fail-closed), но это влияет на доступность.
4. **Узкое окно гонки.** Конкурентный платный запрос, уже прошедший `beginPaidAi`, может завершиться до появления в spool записи другого запроса того же кабинета. Блокировка применяется к следующему `beginPaidAi`, включая каждую fallback-попытку.
5. **Нет UI для диагностики.** `overageRecoveryStatus` доступен на уровне сервиса, страница в кабинете в этот PR не входит.
6. **Внешние API не вызывались.** Платные AI-запросы, публикации VK/Telegram, deploy, SSH и изменения production DB не выполнялись.
