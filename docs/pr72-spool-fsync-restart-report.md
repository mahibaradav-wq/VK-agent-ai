## 1. Причина дефекта

В PR #71 неудавшиеся `fsync` родительских каталогов запоминались в множестве `unsyncedParents` в памяти процесса. При перезапуске множество терялось. Следующий процесс видел уже существующие каталоги: `missingLevels()` возвращала пустой список, и повторный `fsync` их родителей не запускался. Запись синхронизировала только конечный каталог spool после `rename` и объявлялась надёжной (`spooled: true`). После сбоя питания запись о каталоге в его родителе могла не сохраниться, и вместе с каталогом пропадал файл неподтверждённого перерасхода.

Тот же дефект возникает без ошибки `EIO`: процесс создал каталоги и упал до `fsync`. Новый процесс по факту «каталог существует» не может узнать, синхронизирован ли он.

## 2. Архитектура исправления

### Выбор: безусловная синхронизация цепочки вместо маркера

Рассматривались два варианта.

1. **Долговременный маркер или журнал «каталог требует fsync».** Маркер нужно где-то хранить. Если хранить его внутри создаваемой цепочки, он не надёжнее самой цепочки. Если хранить снаружи, его запись тоже нуждается в `fsync` своего каталога. Кроме того, маркер добавляет новые режимы отказа: повреждение, отсутствие, гонки между записью маркера и параллельными писателями, очистка после успеха. И он не решает случай «процесс упал между `mkdir` и записью маркера».
2. **Безусловная синхронизация всей цепочки перед каждой записью.** Состояния нет ни в памяти, ни на диске, поэтому терять или повреждать нечего. Результат не зависит от того, кто и когда создал каталог. Цена — несколько лишних `fsync` каталогов на запись. Запись в spool происходит только когда PostgreSQL недоступен после двух попыток, то есть это не горячий путь.

Выбран вариант 2.

### Реализация (`src/modules/ai/paid-settlement.ts`)

- Множество `unsyncedParents` и `flushUnsyncedParents()` удалены. Состояния в памяти процесса больше нет.
- `ensureSpoolDir()`:
  1. путь нормализуется через `path.resolve`;
  2. недостающие уровни (`missingLevels`) создаются по одному с режимом `0700`, `EEXIST` при гонке допускается;
  3. конечный каталог проверяется `assertSpoolDirSafe` (не симлинк, права `0700`);
  4. **перед каждой записью** `fsync` выполняется для всех предков конечного каталога, от `/` до непосредственного родителя, сверху вниз (`ancestorChain`). Каждый `fsync` фиксирует запись о следующем уровне.
- После `rename` временного файла, как и раньше, синхронизируется сам каталог spool.
- `EINVAL`, `ENOTSUP`, `EOPNOTSUPP` при `fsync` каталога допускаются (`fsyncDirectory`). Любая другая ошибка (`EIO`, `EACCES` при открытии предка и т.п.) прерывает запись: `settlePaidAccount` выбрасывает `PaidSettlementError` с `spooled: false`.
- Уже переименованный файл spool при ошибке `fsync` не удаляется. Он удаляется только после подтверждённой фиксации в PostgreSQL при восстановлении.
- **Параллельные записи.** Каждый писатель сам синхронизирует всю цепочку перед своей записью. `fsync` идемпотентен, общего состояния нет, поэтому координация не нужна и гонок «один синхронизировал, другой положился на это» не бывает. Ошибка `fsync` у одного писателя проваливает только его запись.
- Механизм учёта перерасхода, транзакции PostgreSQL, лимиты AI и провайдеры не менялись.
- `docs/environment.md`: у `AI_SETTLEMENT_SPOOL_DIR` добавлено требование права чтения на всех предков каталога.

## 3. Тестирование перезапуска процесса

Файл: `src/modules/ai/fail-closed-recovery.test.ts`, блок `PR72: spool parent chain fsync survives a process restart`.

**Перезапуск имитируется** через `vi.resetModules()` и свежий `import("@/modules/ai/paid-settlement")`. Это выбрасывает все экземпляры модулей вместе с их состоянием в памяти, как новый процесс. Каталоги и файлы на реальной ФС (во временном каталоге) сохраняются, как на диске после перезапуска. Перехват `FileHandle.sync` (журнал успешных `fsync` и внедрение ошибок) остаётся тем же, потому что реестр `vi.mock` не сбрасывается. Состояние модуля вручную не очищается.

| Тест | Проверка |
|---|---|
| `EIO` на вложенном родителе до перезапуска | процесс 1: `EIO` на `fsync(a)` для `base/a/b/spool` → `spooled: false`, файла нет. Процесс 2: новая запись синхронизирует `/` → … → `base` → `a` → `b` строго сверху вниз, затем `spool` → `spooled: true`. Процесс 3: восстановление → `recovered: 1`, `used = 3` |
| Каталоги, оставленные упавшим процессом без `fsync` | цепочка создана заранее без синхронизации. Первая запись нового процесса синхронизирует всю цепочку до объявления надёжности |
| `EIO` на каждом уровне (`tmp`, `base`, `a`, `b`) | для каждого уровня: отказ → перезапуск → повтор синхронизирует всю цепочку → `spooled: true`. Затем восстановление всех 4 записей |
| `EACCES` при открытии предка | реальная ошибка → `spooled: false` (не путается с неподдерживаемым `fsync`) |
| `EINVAL`/`ENOTSUP`/`EOPNOTSUPP` на всех предках после перезапуска | допускаются → `spooled: true` |
| Параллельные записи (6 шт.) с одним `EIO` на `fsync(a)` | ровно 5 надёжных записей; `fsync(a)` успешно выполнен ровно 5 раз (каждый писатель синхронизировал сам); в каталоге ровно 5 файлов; восстановление → `recovered: 5` |
| Уже переименованные файлы при ошибках после перезапуска | сохранённый файл и файл записи с `EIO` на `fsync(spool)` оба на месте; восстановление в новом процессе → `recovered: 2`, каталог пуст |

Тесты PR #71 обновлены под новую семантику. Для существующего каталога теперь ожидается синхронизация родителя (`base` → `spool`), а повтор после `EIO` синхронизирует всю цепочку (`base` → `a` → `spool`).

Маркер на диске не используется, поэтому тестов его повреждения и отсутствия нет: этого режима отказа в архитектуре нет.

## 5. Оставшиеся ограничения

1. **ФС без `fsync` каталогов.** Если ФС возвращает `EINVAL`/`ENOTSUP`/`EOPNOTSUPP`, запись считается надёжной, но надёжность записей каталогов после сбоя питания этой ФС не гарантируется. Это ограничение ФС.
2. **Права на предков.** Процесс должен иметь право чтения (открытия `O_RDONLY | O_DIRECTORY`) каждого предка до `/`. Иначе любая запись в spool даёт `spooled: false`. Это отражено в `docs/environment.md`. В стандартном Docker-образе `/` и промежуточные каталоги имеют права `755`.
3. **Симлинки среди предков.** `fsync` по пути симлинка синхронизирует каталог-цель. Запись о самом симлинке в его родителе синхронизируется только если родитель тоже в цепочке, а цепочка строится по исходному пути. Сам каталог spool симлинком быть не может (`assertSpoolDirSafe`).
4. **Стоимость.** Глубина пути + 1 `fsync` каталога на каждую запись spool. Записи редкие (только при недоступном PostgreSQL), поэтому стоимость приемлема.
5. **Сетевые ФС** (NFS и т.п.): семантика `fsync` каталогов зависит от реализации. Для spool рекомендуется локальный volume (как `media_data` в production).
6. Внешние API не вызывались.
